## 0. 一句话结论

**表建对了、覆盖也补齐了，但端到端只拿到 +1.6%（926.7 → 941.8 tok/s），没到 950。**

原因不是校准没生效，而是**旧表借用的 T=2048 求解器在 T=3072 上本来就接近最优**（同一形状新旧解只差 0.2%），所以"按真实 T 校准"能拿到的是尾块与真 MISS 那几行，而不是主 chunk 的大块时间。

## 1. 这一轮改了什么

旧表的 14 行 **T bucket 全是 2048**，而引擎在 21K 请求里只跑 **T=3072（对齐 chunk）** 与 **T=268~270（尾块）**。`closest()` 只按 T 做最近邻、N/K/ldy 必须精确相等，于是：

| 问题 | 旧表行为 | 新表 |
|---|---|---|
| T=3072 / T=270 的所有形状 | 借用 T=2048 的求解器，**从未在真实 T 上验证过** | 每个 T 桶都有自己的行 |
| `N=48 K=2560 ldy=96` | 表里只有 `ldy=48`，`closest()` 要求 ldy 精确相等 → **真 MISS，回退 rocBLAS 默认内核** | 新增 `48 2560 96` 全桶，`@3072` 提速 **5.6×** |
| `N=320 K=10240 ldy=320` | 借用 2048 的 `-605553622`，在 3072 上 **refused（status 6）**，连拒 3 次后整形状永久回退默认 | 换成 `-605553618`（1.85 vs 3.13 ms） |
| 其它 prompt 长度的尾块 | 没有任何梯度桶，全部落到最近的 2048 行 | 64 / 128 / 256 / 270 / 512 / 1024 全梯度覆盖 |

新表：**15 个形状 × 8 个 T 桶 = 120 行，113 行带求解器**（`STRATA_ROCBLAS_VERBOSE=1` 实测加载：`rocBLAS tuning enabled (120 rows, 113 with a solution, gfx906, rocBLAS 5.6.0.baa93758)`）。

## 2. 校准过程（纯文本，零代码改动）

`tools/hip/tune_rocblas.cpp` 对每个 (T,N,K,ldy) 枚举 rocBLAS 的全部求解器（该形状 164 个），逐个计时、逐个与默认内核的输出比对（`relative_l2 ≈ 2e-5`、`padding_writes=0`），再把至少快 5% 的写成表行。

- 双卡并行：A 组（重形状）走卡1，B 组走卡3；**120 个 case 约 10 分钟**跑完（单卡要 60+ 分钟）。
- 第二轮补测：第一轮 `--min-gain 1.05` 把"只快 3~4%"的 11 行写成了 `default`，而那正是旧表靠借用解拿到的东西 → 用 `--min-gain 1.0` 只重测这 11 个 case，按实测更快的合并。
- 合并脚本按 `(N,K,ldy,T)` 去重、取增益较大的一行，并校验两卡输出的 header（arch + rocBLAS 版本）一致。

## 4. 为什么端到端只有 +1.6%

这是本轮最重要的一节，也是对我上一份报告预期的一次纠正。

**"vs rocBLAS 默认"不等于"vs 旧表借用的解"**。旧表在 T=3072 上借用的 2048 解，本身就已经很接近该形状在 3072 下的最优：

| 形状 @3072 | 旧表借用解 | 新表解 | 真实差距 |
|---|---:|---:|---:|
| `6144 2560 6144` | 6.031 ms（-605553621） | 6.019 ms（-605553694） | **0.2%** |
| `10240 2560 10240` | 10.158 ms（-605553694） | 10.126 ms（-605553621） | 0.3% |

主 chunk（5 个 3072 chunk）占了整段 prefill 的绝大部分 token，而它本来就没什么肉 → 整机自然也拿不到大提升。

尾块（T=270）确实有真肉（`6144/2560` 12.8%、`10240/2560` 1.2%），但尾块只有 1360 个 token、dense GEMM 在尾块里占比很小（qsa attn 14.7%、gdn 11.6%、gate/up 36%），**dense 省下的几十毫秒在 1255 ms 的尾块里被噪声吞掉**（实测两边尾块都是 ~1255 ms）。

## 6. 一处必须纠正的历史口径错误

我此前把 `tune_i8.sh` 打印的 "GPU timeline 1272 ms" 当成"21K prefill 的 GPU 时间"。实际不是：`tune_i8.sh` 用 `grep "strata prefill timing: 1[0-9]* tokens" | tail -1`，取到的是**最后一个尾块（1360 tokens）**的行。

正确口径（新表）：

- **整段 16720 tokens：GPU 14,886 ms，wall 18.33 s → pp 941.8 tok/s**
- 单个 3072 对齐 chunk：GPU 2,520~2,586 ms
- 尾块 1360 tokens：GPU 1,252~1,273 ms（1360/1.255s ≈ 1,084 tok/s，尾块的 GPU 效率其实比主 chunk 高，因为并行度低时 GEMM 反而更"满"）

以后引用 21K prefill 的 GPU 时间请用 "167xx tokens" 这一行。

## 7. 靶点 ② 的归属更正

上一份 trace 报告 §8 把 `MT16x16x24` / `MT64x64x16` 判为"另一条不走 tuning 的 GEMM 路径"，这是**错的**。这些名字在 strata 源码里根本不存在（`grep MT128x128\|MT64x64\|MT16x16\|cijk` 只命中一处注释），它们是 **rocBLAS 自己的 `Cijk_..._MT…` 默认内核**。

它们的来源正是"没有行 / 行是 default / solution 被拒"三种情况。本轮校准后：

- `g=192x192`（ldc=192 = ldy 96，`48/2560/96` 那个真 MISS）→ 现在有解，0.119 ms；
- `g=640x48`（ldc=640 = ldy 320，`320/10240/320`）→ 不再整形状永久回退；
- 剩下的 `MT16x16x24` 若是 rocBLAS 默认确实最快（例如 `2560/2560 @3072`），加行也无济于事，只能改 tile 选择逻辑。

## 8. 质量

- 求解器的数值一致性在**校准阶段逐个验证**：每个候选解与默认内核在同一随机数据上对比，`relative_l2 ≈ 1.9e-5 ~ 2.4e-5`、`padding_writes = 0`（FP16 输出的舍入量级）。
- `eval100` 28 题回归：见 §8.1（本轮实测，与 `eval100_opt_2026-11-17.jsonl` 基线逐题对照）。

### 8.1 eval100（新表，同一构建连跑 4 次）

| 运行 | MMLU | DROP F1/EM | error | 与基线 pred 不同的题 | 分数变化 |
|---|---|---|---:|---|---|
| A | 58.8% | 90.9% / 90.9% | 0 | mmlu_3, mmlu_42, drop_96 | mmlu_42 0→1 |
| B | 52.9% | 81.8% / 81.8% | 0 | mmlu_3, drop_96 | drop_96 1→0.0034 |
| C | 52.9% | 90.9% / 90.9% | 0 | mmlu_3 | — |
| D | 52.9% | 90.9% / 90.9% | 0 | mmlu_3 | — |
| 基线（旧表，opt1117） | 52.9% | 90.9% / 90.9% | 0 | — | — |

**四次平均分 0.6786 = 基线 0.6786**。三处波动必须如实归类：

- `mmlu_3`：4 次全是 `C → D`，**确定性变化**（换求解器后累加顺序变了），但两边都是 0 分，无影响。
- `mmlu_42`：1 次由错变对、3 次仍错 → 临界题。
- `drop_96`：3 次满分、1 次退化（模型改写成叙述句，F1 0.0034）→ **单次离群**。

也就是说：**没有系统性回退，但 eval100 在这套配置上本身不是确定性的**（`temperature=0` 也不保证，因为引擎的 chunk/前缀缓存状态会改变 prefill 切分与 FP 累加顺序）。这也解释了上一轮 `mmlu_58` 在同一构建内两次给不同答案的现象——任何"单次 eval 涨了/跌了"都不能当结论，要看多次均值。

## 10. 离 950 还差什么（如实算账）

941.8 tok/s 距 950 差 **0.9%**，距 1000 差 6%。按 trace 的分阶段占比（新表 run，整段 16720 tokens / 14886 ms）：

| 阶段 | 占比 | 时间 | 还能不能动 |
|---|---:|---:|---|
| gemm gate/up（i8） | 35.5% | 5,284 ms | 已到边际（上轮 +32% 单算子只换来 +9% 整机） |
| qsa attn | 14.1% | 2,093 ms | 未分析 |
| gdn / gdn recurrence / gdn out proj | 24.2% | 3,598 ms | recurrence 是 32 线程半 wave + 每 token 32 步依赖链，改动高风险 |
| qsa proj + router+shared + ple + hc read | ~14% | ~2,000 ms | 已是校准过的 rocBLAS 形状 |
| widen_rows_f16（FP16→FP32 原地扩写） | ~1.8% | ~270 ms | **唯一"确定性、低算术风险"的 1.8%，做完刚好过 950**，但要下游改吃 FP16 |

结论：**表这条路已经挖完**（主 chunk 新旧解只差 0.2%，没有别的形状可校准）。要继续冲，只能动 `widen_rows_f16`（+1.8%，需改下游 consumer）或 GDN 递推（7%，高风险，会改算术顺序）。
