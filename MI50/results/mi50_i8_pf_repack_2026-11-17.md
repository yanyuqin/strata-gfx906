## 1. 方案 4：三级预取（PF）

### 1.1 实现

`i8_kernel` 增加模板参数 `PF`（预取深度，stage 数）：

- 共享内存**仍是双缓冲**（50 KB，1 block/CU 不变）；深度放在**原始寄存器**里（PF 份 `wraw` / `ar`），所以零 smem 代价、不降占用率。
- 流水：stage k 在 stage `k-PF` 期间发起全局读，在 stage `k-1` 末尾转成 smem，在 stage `k` 消费。PF=1 时逐字等于原实现（`(st+1)%1 == 0`），PF=2 即"计算中 / 已就绪 / 在飞"三级。
- 运行时开关 `STRATA_I8_PF`（默认 2），A/B 不需要重新编译。

### 1.2 第一版实现是错的（必须记录）

第一次只加了深度、**没有展开 stage 循环**：`wraw[(st+PF)%PF]` 是运行时下标，寄存器数组只能靠 `v_cndmask` 选路。实测 **PF=2 比 PF=1 慢 16%**（871.2 → 729.4 tok/s，GPU 1344 → 1745 ms）。

修法：`#pragma unroll 2`（`I8_ST_UNROLL`）展开 stage 循环，使 `st % PF` 成为每个副本的编译期常量。修正后 PF=1 858.3 / PF=2 868.1。

### 1.3 VGPR / spill 验证（元数据，gfx906 设备目标文件）

用 `clang-offload-bundler` 从 `.hip_fatbin` 解出 `dev.o`，读 `.note` 里的 amdhsa 元数据：

| 实例（Q4_K，TM=4） | VGPR | spill | private segment |
|---|---:|---:|---:|
| PF=1, N8=0 | 150 | 0 | 0 |
| **PF=2, N8=0** | **193** | **0** | **0** |
| PF=1, N8=1 | 167 | 0 | 0 |
| **PF=2, N8=1** | **210** | **0** | **0** |

193 / 210 都在每 SIMD 256 VGPR 的上限内，**没有溢出、没有 scratch**，占用率（1 wave/SIMD，4 waves/CU）不变。所以 PF 的收益上限本来就只有"多覆盖一个 stage 的延迟"，而实测只值 ~1%。

两条记录别混：离线 amdhsa 元数据（上表）是编译产物自己的数，**193 VGPR / 0 spill** 是它的口径；rocprofv3 `--kernel-trace` 的 `VGPR_Count`/`Scratch_Size` 读的是运行时 dispatch 描述符，同一实例给的是 **164 / 112 B**。两者口径不同（profiler 的 scratch 列还含固定私有段），本报告以编译期元数据为准；112 B 这个差我没有追到底，不影响结论（`native_i8_parity` 与整机吞吐都没有溢出退化迹象）。

### 1.4 正确性与噪声带

`native_i8_parity`（默认 PF=2）全格式 × 三档 tile（2/3/4）通过：`all ok`，最差相对 RMS 2.6e-3（对 grouped 内核的既定容差），且每次调用三次重跑同比特。PF 不影响算术顺序，输出逐位一致。

吞吐上必须把噪声带写清：PF=2 第一次 868.1 tok/s，同日重跑同一配置 830.1 tok/s（−3.3%），PF=1 是 858.3。**即 PF=2 的收益在 ±4% 的日间噪声带里，不能算作"提速"**；它的价值在于"不改算术、不涨 VGPR、不掉占用率"的前提下把三级流水打通，为后面改 occupancy 留了接口。

## 2. 方案 2：strata-pack 权重重排

### 2.1 布局

把一个专家的权重按 **`[section][tile 64 行][stage 128 值][行][记录]`** 存放，一个 (tile, stage) 就是连续的一块（Q4_K 5,120 B；Q5_1 6,144 B）：

| 格式 | 记录字节 | 组成 |
|---|---:|---|
| Q4_K (12) | 80 | header 16（d, dmin, 12 scale） + 本 stage 的 64 个码字节 |
| Q5_K (13) | 112 | header 16 + 超块全部 32 个 qh 字节（每个 stage 都要读） + 64 码字节 |
| Q5_1 (7) | 96 | 本 stage 的四个 24 B 块（行内本来就连续，纯搬运） |
| Q8_0 (8) | 144 | 四个 34 B 块（136） + 8 B pad |

三个 section：gate（n_ff 行）、up（n_ff 行）、down（n_embd 行）。镜像总量 +6.7%（Q5_1 down）/ +8.6%（Q8_0 down）。

### 2.2 与 Decode 的兼容（用户特别要求守住的点）

**本次刻意不碰 decode**：`native_gu_kernel` / `native_down_kernel` / `row_dot` 继续读**原始 blob**，packed 镜像只给 `native_expert_i8` 用（`pk_base` / `pk_stride` / `pk_up_off` / `pk_dn_off` 四个新参数，`pk_base == nullptr` 时逐字等价于旧路径）。

代价是显存里多一份镜像：ring 是 530 MB 量级（`ring_bytes()`），翻倍约 +530 MB / 双卡 → 每卡 ~265 MB，可接受。

是否把 decode 也迁到 packed 布局（用户提到的 66.5 → 80+ t/s）**留作下一步**，前提是先证明 prefill 侧确有收益——而本次实测表明没有，所以这一步现在做没有依据。

### 2.3 正确性（隔离基准 `i8_pack_bench`）

同一批 blob、同一批 entry，跑"原布局"与"packed 布局"两次，逐浮点比较：

```
Q4_K / Q5_1 down : blob 3072000 B, packed 3276800 B (+6.7%)
   parity: 3932160 floats bit-identical, 0 different
Q4_K / Q8_0 down : blob 3584000 B, packed 3891200 B (+8.6%)
   parity: 3932160 floats bit-identical, 0 different
```

### 2.4 时间（同一基准，1536 entry × 16 blob × 30 次，3 轮 × 3 次重跑取均值，`STRATA_I8_TM=4 STRATA_I8_N8=0 STRATA_I8_PF=2`）

| 用例 | 原布局 | packed | 差 | 带宽（原布局 → packed） |
|---|---:|---:|---:|---:|
| Q4_K / Q5_1 | 2.177 ms | 2.200 ms | **+1.1%** | 22.6 → 22.3 GB/s |
| Q4_K / Q8_0 | 2.130 ms | 2.137 ms | **+0.3%** | 27.0 → 26.8 GB/s |

三次重跑分别 +1.4 / +1.2 / +0.9%（Q5_1）、+0.1 / 0.0 / +0.8%（Q8_0）：**packed 稳定地略慢 0.3~1.4%**，不是提速。镜像还多占 6.7%（Q5_1）/ 8.6%（Q8_0）显存。

> 记账要点：同一用例绝对毫秒数会随 GPU 时钟状态漂 3~5%（本文件早先一轮记的是 2.09 ms），**只有同一次调用里 blob/packed 的比值可信**（±1%）。另外 `i8_pack_bench` 传的 `cap_groups == cap_entries`，使内核自选 tile 的 `avg = 1` 落到 TM=2；本轮为对齐生产档显式指定 `STRATA_I8_TM=4`，否则测到的是最小 tile 实例。

### 2.5 rocprofv3 硬件计数器：读请求本来就是整条 128 B 线

`/opt/rocm/bin/rocprofv3 --pmc TCC_EA_RDREQ_sum --kernel-trace`（1.3.5，gfx906 上有该计数器；`TCC_EA_RDREQ_32B_sum` 在本卡恒为 0，故按 128 B/请求折算）：

| 实例（TM=4，N8=0，PF=2） | dispatch | ms/次 | EA 读请求/次 | 折算读入 | 有效带宽 | VGPR | 该读的权重 | 读入/应读 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `i8_kernel<12,true>` gate+up | 40 | 1.27 | 265,783 | 34.0 MB | **26.7 GB/s** | 164 | 29.49 MB | 115% |
| `i8_kernel<7,false>` Q5_1 down | 20 | 0.76 | 184,921 | 23.7 MB | **31.0 GB/s** | 168 | 19.66 MB | 120% |
| `i8_kernel<8,false>` Q8_0 down | 20 | 0.69 | 258,613 | 33.1 MB | **47.8 GB/s** | 184 | 27.85 MB | 119% |

三个结论直接落地：

1. **请求粒度没问题**：每个 (tile, stage) 的 5~7 KB 在旧布局里也被整条 128 B 线吃掉，"小读放大"最多 15~20%，改连续块能省的只有这 15~20% 里的一部分——这就是 pack 只有 ±1% 的原因。
2. **带宽离目标差一个数量级**：26.7~47.8 GB/s，MI50 HBM2 峰值 1024 GB/s，占 2.6~4.7%；用户要求的 350+ GB/s 没有达到，而且是在地址已经连续的前提下达不到。
3. **同一份权重，down 比 gate/up 快**：down 的行距更短（Q5_1 480 B/行、Q8_0 680 B/行，gate/up 1440 B/行），Q8_0 down 拿到 47.8 GB/s。说明真正卡住 gate/up 的不是地址跨度而是"每 stage 一次 barrier + 1 block/CU"。

## 3. 为什么重排没用：算一下就清楚

单卡实测 **3.47 TMAC/s**（7.55e9 MAC / 2.177 ms）。MI50 dp4a 峰值 ~26.5 TMAC/s → **13.1%**。

按 stage 拆（1 block/CU，60 CU）：

- 每 stage 每 block：64 行 × 64 entry × 128 值 = 524,288 MAC
- 每 stage 每 block 的 **LDS 流量**：256 线程 × 4 blk × (4×(32+16) + 4×(4+32)) = **344 KB**
- 每 CU 串行 ~240 stage（14,400 stage / 60 CU），实测 ~9 μs/stage
- LDS 需求 344 KB / 9 μs = **38 GB/s**，而 MI50 LDS 上限 ~179 GB/s（128 B/clk）→ 21%
- dp4a 需求 524,288 / 9 μs = 58 GMAC/s，上限 442 GMAC/s → 13%
- **全局读**：每 stage 权重只有 5 KB，9 μs → 0.6 GB/s/CU，整卡 24 GB/s（rocprofv3 实测 26.7）

三项都没打满，唯一的解释是**延迟暴露**：1 block/CU、4 waves，每 stage 结尾一次全 block barrier；权重与激活的全局读（跨 1.3~3.0 KB 行距）延迟 ~1 μs 量级，只能被一个 stage 的计算（~0.3 μs）掩盖。PF=2 把掩盖拉到 2 个 stage，只换来 1%；因为再深也没有第二个 block 可以切换。

**共享内存这一侧的实测**（`smem_attr` 探针，gfx906 两块卡）：`MaxSharedMemoryPerBlock = 65536`、`SharedMemPerBlockOptin = 65536`、`MaxPerCU = 65536`。按 `I8Smem<12,TM>` 展开：TM=2 39,952 B、TM=3 45,600 B、TM=4 **51,232 B**——所以 TM=4 起得来（`i8_smem_limit()` 读到 65536，不会被夹回 TM=2/3），但它占掉 78% 的 64 KB LDS，**2 blocks/CU 需要 ≤32 KB**，这就是"必须把 smem 压到 32 KB"这条建议的硬依据。

**所以真正的杠杆是"能塞进 2 个 block/CU"**（≤32 KB smem），而不是地址布局。Q4_K 的行距 1,440 B、stage 内 32 B 连续，虽然没有达到理想合并，但整行 128 B 线最终被四条指令全部用完——**字节利用率本来就是 100%**（rocprofv3 实测读入/应读 = 115~120%），这也是重排无效的根本原因。

## 4. 下一步（按收益/成本排序）

1. **压 smem 到 32 KB 换 2 blocks/CU**（收益预期最大，改动中等）：`s_r` 记录 20→16 dwords（源码 s_src 另置 64 ints）、激活阶段改单缓冲、W 的 4 dword pad 视 bank 冲突决定去留。50 KB → 约 33 KB，两个 block 交替掩盖延迟。
2. 若 2 blocks 仍不够：把 `I8_KS` 128 → 64，缩短单 stage 的串行长度，让 barrier 更频繁但每次更浅（与 1 配套调）。
3. 变体 B（tile 8，128×128，8+32 次 b128 读/512 dot）目前被 `i8_tile8_type` 排除在 K-quant 之外——把它扩到 Q4_K 是另一个数量级的改动，且需要重验。

## 9. 2 blocks/CU：压 LDS + 压 VGPR 的实测账单（本轮新增）

### 9.1 生死线：VGPR 到底是多少

从 gfx906 目标的 `.hip_fatbin` 解出 amdhsa 元数据（`llvm-objcopy --dump-section` + `clang-offload-bundler`，再 `kd_vgpr.py` 解析 msgpack），实测（`1BUF=0`，即原双缓冲）：

| 格式 / TM | NR=0 PF=1 | NR=1 PF=1 | NR=0 PF=2 |
|---|---:|---:|---:|
| T=12 gate/up TM=2 | **126** | **124** | 135 |
| T=12 gate/up TM=3 | 141 | 148 | 150 |
| T=12 gate/up TM=4 | 155 | 174 | 164 |
| T=7 (Q5_1) down TM=2 | **120** | **121** | 140 |
| T=7 down TM=3 | 134 | 145 | 154 |
| T=7 down TM=4 | 148 | 171 | 168 |
| T=8 (Q8_0) down TM=2 | **118** | **121** | 155 |
| T=8 down TM=3 | 131 | 145 | 168 |
| T=8 down TM=4 | 144 | 170 | 181 |
| T=13 (Q5_K) down TM=2 | 136 | 134 | 136 |

**三条硬结论**：

1. **只有 TM=2 + PF=1 能在不强制的情况下进 128**（118~126）。TM=3 起全部超标，TM=13 的 down 即使 TM=2 也要 136。
2. **PF=2 只贵 9~21 个 VGPR，不是先前报告写的 43 个**。§1 里"193 / 210"那组数字属于旧构建或别的格式，本轮实测作废（T=12 TM=4：155 → 164，差 9）。
3. 单缓冲（`1BUF=1`）**几乎不改变 VGPR**（每个配置 −1）。所以"压 LDS"与"压 VGPR"是两条独立的账，靠单缓冲省不出寄存器。

### 9.2 强制 2 blocks：`__launch_bounds__(256, 2)`

加 `I8_MINB` 宏后，编译器把所有配置都压到**正好 128 VGPR**：

| 配置（`1BUF=1` + `I8_MINB=2`） | VGPR | 单算子（1536 entry × 30 reps） |
|---|---:|---|
| T=12 TM=2 PF=1 gate/up | 125 | — |
| T=12 TM=3 PF=1 | 128 | — |
| T=12 TM=4 PF=1 | 128 | — |
| T=7 TM=2 / TM=3 / TM=4 | 119 / 128 / 128 | — |
| TM=4 PF=1 单算子 | — | **2.82 / 2.74 ms**（比不强制慢 34%） |
| TM=3 PF=1 单算子 | — | **1.35 / 1.34 ms**（最快） |
| TM=2 PF=1 单算子 | — | 1.42 / 1.44 ms |
| TM=4 PF=2 单算子 | — | 3.56 ms（Q8_0，最差） |

**TM=4 被强制到 128 后需要 spill 27 个寄存器，代价压过了 2 blocks 的收益**；TM=3 只需压 2~12 个，反而最快；TM=2 无须压，稳定。

### 9.3 LDS 账单

`I8Smem<T,TM>::bytes`（含 16 B grid 表、s_src 借用 s_r 的 pad）：

| | 双缓冲 | 单缓冲（`I8_SMEM_1BUF=1`） |
|---|---:|---:|
| TM=2 | 39,952 B | **20,496 B** |
| TM=3 | 45,600 B | 22,800 B |
| TM=4 | 51,232 B | 25,616 B |

gfx906 每 CU LDS = 65,536 B。单缓冲后 TM=2 两块 = 40,992 B（62.5%）、TM=4 两块 = 51,232 B（78%）——都进得去。**但双缓冲下 TM=2 两块要 79,904 B，物理上不可能**，所以"2 blocks + 单屏障"这条路在 TM=2 下不存在，只能二选一。

### 9.4 单缓冲改了什么

`I8_SMEM_1BUF=1` 时 `NBUF=1`：`s_w`/`s_a`/`s_r`/`s_d`/`s_s` 全部一份，每个 stage 两次 `__syncthreads()`（原来一次）：

```
for st:
    compute(st) 读 s_w / s_a / s_r          // 单缓冲：读完才能覆写
    __syncthreads()                          // ①
    store(st+1) 写 s_w / s_a / s_r          // PF 预取的寄存器 → smem
    __syncthreads()                          // ② 下一轮可见
```

代价是 stage 级流水被彻底串行化，收益是第二个 block 能在 ① 处接管 SM。**单 block 时这一改是纯亏：TM=4 单缓冲 21K prefill 847.2 tok/s，比双缓冲 858.3 低 1.3%**——正好量化了"双缓冲值多少"。

## 10. 三条待纠正的既有判断

1. **"PF=2 多占 43 个 VGPR"**：实测只多 9（T=12 TM=4：155 → 164）。"150→193 / 167→210"这组数字与当前构建不符，作废。
2. **"TM=2/3/4 算力几乎无差，可放心降到 TM=2"**：双缓冲下 TM=2 是 779.7、TM=4 是 858.3，**差 6.1%**，不是噪声。TM=2 只有在配合 2 blocks/CU 时才有意义（906.4 vs 847.2）。
3. **"rocBLAS 校准表还没合入 gfx906"**：**已经在用**。`cmake/hip_backend.cmake:85` 在 `TARGET roc::rocblas` 时置 `STRATA_ROCBLAS_AVAILABLE ON`，`gfx906-rocblas.txt` 有 14 个形状（13 个带 solution），引擎日志每卡都打印 `prefill gemm: rocBLAS tuning enabled (14 rows, 13 with a solution, gfx906, rocBLAS 5.6.0.baa93758)`。**858 tok/s 这一档本身就含它的收益**，不能重复计入"再涨 8~13%"。
4. **"每个 stage 两次 `__syncthreads()`，合并成一次能省 15~20%"**：原双缓冲 shape 下 stage 内**只有一次**（写 b^1 与读 b 不冲突），不存在冗余屏障；单缓冲后才需要两次，且那两次是正确性必需，不是可合并的冗余。
