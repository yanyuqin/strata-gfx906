## 0. 先说数据可靠性

- 抓到 **163,102 个 KERNEL_DISPATCH**（Agent 1 = 45,759；Agent 3 = 117,343）。
- rocprofiler-sdk 在记录 kernel 时间戳时会 serial 化 dispatch 队列，**每个 kernel 被放大约 11 倍**：两卡 busy 合计 27,463 ms，而正常 21K 的 GPU timeline 是 1,272 ms。日志里引擎因此触发自己的 native verify watchdog（`verify: timed out at layer 1 ... did not finish within 5 s (#267)`），请求在最后一个 chunk 前被中止。

两个结构性问题：

1. **`closest()` 要求 N/K/ldy 精确相等，只有 T 是最近邻**（`rocblas_tuning.hpp:105`）。所以 `N=48 K=2560 ldy=96` 匹配不到表里的 `48 2560 48 2048`——ldy 从 48 变成 96 就整行失效，回退到 rocBLAS 默认 kernel。
2. **表里 14 行的 T bucket 全是 2048**，而实际跑的是 **T=3072**（主 chunk）和 **T=270**（尾块）。也就是说：13 个 solution 都是在 2048 上测出来的，在 3072 与 270 上**从未被验证过**，只是被 `closest()` 顺手复用了。这不是"命中"，是"借用"。

## 7. 靶点 1b：尾块形状的实测退化（4K trace，3072 对齐 vs 273 尾块）

同一个 kernel 在两个 M 上的每 tile 成本（trace 放大后，但同一 trace 内的相对比较有效）：

| kernel | 对齐 g=…x24（3072 tok） | 尾块 g=…x3（273 tok） | 每 tile 成本比 |
|---|---|---|---|
| `cijk MT128x128x16 SE` g=20480 | 3,656.9 µs / 24 tiles = 152.4 | 384.2 µs / 3 tiles = 128.1 | **0.84×（尾块更快）** |
| `cijk MT128x128x16 SN` g=12288 | 6,342.7 / 24 = 264.3 | 968.9 / 3 = 323.0 | 1.22× |
| `cijk MT128x128x32 SN` g=768 | 2,836.3 / 24 = 118.2 | **1,434.5 / 3 = 478.2** | **4.05×（严重退化）** |
| `cijk MT64x64x16 SN` g=640 | 1,391.8 / 48 = 29.0 | 321.7 / 5 = 64.3 | **2.22×** |
| `cijk MT16x16x24 SN` g=64 | 513.1 / 192 = 2.67 | **334.6 / 17 = 19.7** | **7.35×（最严重）** |

`MT128x128x32 SN g=768x3`：尾块只算 273 个 token（工作量是对齐 chunk 的 8.9%），却花掉对齐 chunk **50.6%** 的时间（1434.5 vs 2836.3 µs）。
`MT16x16x24 SN g=64x17`：工作量 8.9%，耗时 65%。

尾块相关条目合计占 trace busy 的 **≈3.5%**（137.7 + 32.1 + 30.9 + 51.1 + 43.9 ms）。按等比压缩估算，真实可回收 **2~3%**。

这两个家族**完全没有出现在 verbose 的命中表里**，说明它们不走 `Gemm::f16_inplace`（因此不经过 `try_rocblas_f16o`），是另一条 GEMM 路径上 rocBLAS 的默认选择：

|---|---:|---:|---:|---:|---|
| `MT16x16x24 SN` g=192x192 w=64 | 360 | 944.9 | 340.16 | 1.2% | 3072×3072，16×16 tile |
| `MT16x16x24 SN` g=64x192 w=64 | 480 | 511.6 | 245.57 | 0.9% | 1024×3072 |
| `MT16x16x24 SN` g=64x17 w=64 | 96 | 334.6 | 32.12 | 0.6% | 1024×273（尾块） |

## 9. 靶点 2：PLE 头的通路与"FP32 写出"的真相

通路（`src/prefill/gemm.cu`）：`Gemm::f16_inplace` → `try_rocblas_f16o`（命中就用 solution）→ 未命中则 `cublasGemmEx`（`CUDA_R_16F` 输出，`ldc = 2*ldy`）→ **然后一律跑 `widen_rows_f16`**，把 FP16 结果原地扩成 FP32 填满整行。

```cpp
cublasGemmEx(..., Y, CUDA_R_16F, (int)(2*ldy), ...);   // FP16 written into the first half of each FP32 row
widen_rows_f16<<<T, 256>>>(Y, N, ldy, ...);            // in place: read half, write float
```

`widen_rows_f16` 是每 block 一行、行内 256 列一块、**每块两次 `__syncthreads()`** 的原地扩张，实测占 trace busy **1.8~2.1%**（`g=786432x1x1`，21K 里 3,910 次 / 535 ms）。

三处需要修正你的判断：

1. **PLE 的 N 不是 40960，是 10240**（verbose 实测 `T=3072 N=10240 K=320 ldy=10240`）。trace 里 `g=20480x24` 的 `SE` 变体 grid_x = 2×N，所以看起来像 20480。
2. **它已经在用校准 solution**（-605553696），不是未调优的默认 kernel。那 8.8% 是 GEMM 本体的计算时间，不是"因为走了 FP32 写出"。
3. **FP32 写出的代价只有 1.8%（widen），不是 8.8%。** 只把输出改成 FP16（下游能吃的话）最多回收 1.8%：906 → 922 tok/s，**到不了 950**。要把 PLE 的 8.8% 打下来，得让那个 K=320 的瘦长 GEMM 本身更快（K 只有 320，MT_K=16 时只有 20 个 K-tile，累加链短、无法掩盖延迟），而不是改输出格式。

## 10. 靶点 3：QSA / GDN 的发射与占用特征

| kernel | 形状 | 观察 |

| **`prefill::gdn_rec_cols_pipe_kernel`** | g=6144x4x1, **w=32** | **5.8%**，单次 4,452~7,418 µs。`CB*RG = 32` → **半个 Wave64**，占用率天然只有 50%。源码注释写明 64 线程的 `gdn_rec_cols_warp_kernel` 只对 Volta（cc 7.0）开放，gfx906 走的是 32 线程的 pipelined 版 |
| `prefill::gr_write_norm_rs_kernel` | g=**3145728x1x1**, w=256 | 1.1%，每 block 只处理极少量元素：**发射碎片** |

GDN 这条线的瓶颈是**每 token 一条 32 步的依赖 FFMA 链 + 4 次 `__syncthreads()`**（源码注释原话："the recurrence's per-token floor"），216 次 dispatch × 7.4 ms。它不是访存问题，是串行依赖问题。
